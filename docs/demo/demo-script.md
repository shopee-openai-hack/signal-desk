## A. Q&S（前 30 秒逐字稿）

**Q（問題）：**
> 一位負責 listing 的 Operation 營運人員，在中聯油脂事件的 13 天內面對清單改五次、受影響品項從 15 項變成 440 項，最後約三分之二批次其實沒問題，而官方退費指南又沒列任何電商；他每次都得重新找證據、重做商品清單，還要避免下架錯商品。

**S（解法）：**
> 我們的案件 agent 從弱訊號建案，自己查證並比對批號，碰到下架就停下來等人核可，範圍擴大時要求重新核可，放行證據進來時自己縮小範圍，同時保留每次判斷與已執行的安全動作。

## B. 一畫面、三工具、一迴圈、一核可節點

| 元素 | 內容 |
|---|---|
| 那一個畫面 | 案件詳情：左側時間軸，右側候選商品清單；頁首同時顯示業務影響、優先級、案件狀態與「回放：2026-06-30 至 2026-07-21」 |
| 工具 1 | 外部證據查核：可查核陳述與來源 → 支持、反駁或證據不足，附來源與時間 |
| 工具 2 | 商品比對：已查核陳述、品牌與批號 → `candidate`、`confirmed`、`excluded` 與缺失資訊 |
| 工具 3 | 模擬下架執行：已核可的案件版本與商品 ID → 商品改為 `delisted` 並寫入執行結果 |
| 迴圈 | 新訊號 → 歸入案件 → 查核證據 → 更新優先級與商品範圍 → 人員核可 → 執行 → 繼續追蹤 |
| 核可節點 | 每次下架前停下等 listing 營運人員核可；核可綁案件版本與商品清單，新增候選需重新核可 |

### 決勝一幕操作卡

- **注入什麼：** Stage 6 中央社報導，帶入「30 批中 19 批合格放行」的反駁證據。
- **期待 agent 的反應：** 把模擬批號 `315-1150411` 的 `prod_009` 改為 `excluded`，案件由 `critical` 降為 `high`；保留 `315-1150404` 的 confirmed 判斷、三筆 `delisted` 狀態及尚缺批號的候選。
- **觀眾看得到的證據：** 案件頁首的優先級變化、候選商品列的 relation 與理由、重新整理後的商品狀態，以及保留 Stage 5 舊判斷的時間軸。

## E. 評審 Q&A

| 可能的提問 | 誰答 | 一句話答案 |

| 為什麼不是規則引擎？ | 主講人 | 難點是公告清單在 13 天內改五次，agent 要依新證據做批號級判斷、自動重排候選與下一步，並解釋每次改判，固定規則只能覆蓋已知格式。 |
